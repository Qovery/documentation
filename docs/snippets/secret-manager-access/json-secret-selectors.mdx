### Selecting a value from a JSON secret

Set `json_target_key` when creating or updating an external secret through the variable API to inject one value from a JSON document. The secret is fetched inside your cluster at deployment time.

| Surface | Field | Type |
| --- | --- | --- |
| Variable API requests and responses | `json_target_key` | String or `null` |
| q-core variable fields | `jsonTargetKey` | `String?` |

q-core stores the selector as supplied and sends it to the deployment engine, which converts it into an ESO property expression. Send the member path shown in these examples; full GJSON queries are not supported.

<Info>
  JSON selection requires API and deployment engine versions that support `json_target_key`. Generated API schemas, SDKs, Console, CLI, and Terraform provider support are updated separately. The examples below use the variable API directly.
</Info>

#### Create an external secret with a JSON selector

For example, the remote secret `/production/config` can contain:

```json
{
  "database": {
    "credentials": {
      "password": "secret-db"
    }
  },
  "accounts": [
    { "password": "secret-account" }
  ],
  "database.password": "secret-dotted-key",
  "api*key": "secret-api",
  "back\\slash": "secret-backslash"
}
```

The following request body for `POST /variable` creates a variable named `DATABASE_PASSWORD` whose value at deployment will be `secret-db`:

```json
{
  "key": "DATABASE_PASSWORD",
  "value": "/production/config",
  "is_secret": false,
  "variable_scope": "CONTAINER",
  "variable_parent_id": "00000000-0000-0000-0000-000000000002",
  "secret_manager_access_id": "00000000-0000-0000-0000-000000000001",
  "mount_path": null,
  "json_target_key": "database.credentials.password"
}
```

Replace `variable_parent_id` with your container's ID and `secret_manager_access_id` with the ID of its Secret Manager Access. The `value` field identifies the remote secret; `json_target_key` selects a value inside it. `is_secret` stays `false` for external secrets: Qovery stores the reference, while ESO fetches the secret value inside your cluster.

API responses return the original selector in `json_target_key` and keep `/production/config` in `value`. They do not return the selected password.

To create other variables from the same remote secret, change `key` and `json_target_key`:

| `json_target_key` as a JSON string | Injected value |
| --- | --- |
| `"database.credentials.password"` | `secret-db` |
| `"accounts.0.password"` | `secret-account` |
| `"database\\.password"` | `secret-dotted-key` |
| `"api*key"` | `secret-api` |
| `"back\\\\slash"` | `secret-backslash` |

Dots separate object members. Numeric segments select array elements, starting at `0`. A secret whose root is an array can use `0.password` to select the first element's `password`.

To select a key containing a literal dot, escape it with `\.`. JSON strings need an additional escape, so the request contains `"database\\.password"`. A literal backslash is written as `\\` in the selector and `\\\\` inside a JSON string. Backslashes before other characters remain literal for compatibility with existing key names.

Other characters, including `*`, `?`, `#`, `@`, and `|`, are literal key characters. Filters, wildcards, and transformations are not evaluated. Nested selection is explicit: `database.credentials.password` selects the nested member, while `database\.password` selects the literal key `database.password`, even when both kinds of key exist in the same document.

#### Update or clear the selection

Use `PUT /variable/{variableId}` to replace the selector. This request changes `DATABASE_PASSWORD` to select `secret-account` from the same remote secret:

```json
{
  "key": "DATABASE_PASSWORD",
  "value": "/production/config",
  "secret_manager_access_id": "00000000-0000-0000-0000-000000000001",
  "json_target_key": "accounts.0.password"
}
```

Include the existing selector in every update that should preserve it. Omitting `json_target_key` or setting it to `null` clears the previous selection and restores whole-secret behavior. To clear it explicitly:

```json
{
  "key": "DATABASE_PASSWORD",
  "value": "/production/config",
  "secret_manager_access_id": "00000000-0000-0000-0000-000000000001",
  "json_target_key": null
}
```

Omitting the selector or sending `null` on creation also selects the complete remote secret. An empty string is rejected.

#### Validation and compatibility

A non-null selector must:

- Contain between 1 and 256 Unicode characters.
- Have no empty path segments, such as `.password`, `database.`, or `database..password`.
- Have no control characters or leading or trailing whitespace.
- Have no trailing unescaped backslash.

`json_target_key` applies only to external secrets injected as environment variables (`EXTERNAL_SECRET`). It cannot be combined with `mount_path`, used with a file external secret (`FILE_EXTERNAL_SECRET`), or used for ordinary variables or built-in secrets.

q-core validates the selector syntax and the remote secret reference without reading the secret value. If the selected property does not exist, ESO reports the error during deployment. Changing the remote JSON still requires a redeploy before the running service receives the new value.

Environment and service clones preserve the selector. Existing variables and old deployment snapshots without this field keep whole-secret behavior. CSV imports do not set a selector.

The Terraform exporter includes `json_target_key` when a selector is set. Applying the exported configuration requires a Terraform provider version that accepts this field. Deploy the engine update before enabling JSON selection in the API.

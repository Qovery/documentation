---
title: "Auto-Deploy"
description: "Turn on auto-deploy so each Git commit redeploys your service, filter which commits trigger it, and call the Qovery API to deploy new container image tags."
---

Qovery can automatically update the services that deploy from a Git repository (applications, jobs, Helm charts, Terraform services, and containers built from Git) to the latest version of their Git branch. Each time a commit is done on your Git repository, Qovery will receive a webhook call with the commit information and will determine which services should be automatically re-deployed. With auto-deploy on, anyone who can push to the branch can deploy the service.

## Activation

<Tabs>
  <Tab title="Console">
You can activate the auto-deploy flag either within the application settings or during the service creation flow.

![Auto-Deploy Settings](/images/deployment/auto-deploy-settings.png)

![Auto-Deploy Creation Flow](/images/deployment/auto-deploy-creation-flow.png)

The Console does not offer auto-deploy for containers built from Git yet: use the API or Terraform.
  </Tab>

  <Tab title="CLI and API">
    You need the [Qovery CLI](/cli/overview), signed in with `qovery auth`. The `qovery api` command sends authenticated requests to the [Qovery API](/api-reference/introduction).

    Turn on auto-deploy for an application:

    ```bash
    qovery application update -n my-app --auto-deploy
    ```

    Pass `--auto-deploy=false` to turn it off. The command uses the organization, project and environment of your CLI context (`qovery context set`), or the `--organization`, `--project` and `--environment` flags.

    For a container built from Git, set `auto_deploy` with `PUT /container/{containerId}`. The request replaces the container's settings (ports and storage left out are deleted), so send the body that `GET /container/{containerId}` returns, with `auto_deploy` changed:

    ```bash
    CONTAINER_ID="REPLACE_WITH_CONTAINER_ID"  # from qovery container list --json

    qovery api "container/$CONTAINER_ID" \
      | jq '.auto_deploy = true' \
      | qovery api "container/$CONTAINER_ID" --method PUT --input -
    ```

    If a deployment of the container finishes between the `GET` and the `PUT`, the `PUT` returns 400: run the command again.
  </Tab>

  <Tab title="Terraform">
    Set `auto_deploy` on your `qovery_application` resource and run `terraform apply`:

    ```hcl
    resource "qovery_application" "my_app" {
      # ...
      auto_deploy = true
    }
    ```

    On a `qovery_container` built from Git (`source.git_repository`), `auto_deploy` defaults to `false`: set it to `true` to deploy the container on every push (provider 1.11.0 and later).
  </Tab>
</Tabs>

### Check it worked

Read the application with `GET /application/{applicationId}`:

```bash
APPLICATION_ID="REPLACE_WITH_APPLICATION_ID"  # from qovery application list --json

qovery api "application/$APPLICATION_ID"
```

The response contains `"auto_deploy": true`. Push a commit to the application branch, then run `qovery environment deployment list --environment "<environmentName>"`: a new deployment for that commit appears in the list.

Once activated, each commit on the application branch will automatically trigger the deployment of the new version of your application.

## Webhook Warnings

When you save the settings of an application, job, Helm chart, or Terraform service, the Console displays a warning if the auto-deploy webhook could not be set up. The settings are saved, but pushes to the repository will not trigger deployments until the issue is fixed.

| Warning | Meaning | What to do |
|---------|---------|------------|
| Auto-deploy webhook not created (permission) | The Git account used by the service does not have admin rights on the repository, which are required to create the webhook. | Ask a repository admin to save the change, or use a Git token with admin rights. |
| Auto-deploy webhook not created (setup failed) | Qovery could not create the webhook on the repository. | Check the webhook status in the auto-deploy settings. |
| Git account changed | The previous Git account can no longer access the repository, so your Git account is now used for the service. | No action required, unless you want to use another Git account. |

## Filtering Commits

The "Deployment restrictions" feature allows you to better control which commits should trigger a new deployment and which should not. It applies to every service that deploys from a Git repository: applications, jobs, Helm charts, Terraform services, and containers built from Git.

![Deployment Restrictions](/images/deployment/deployment_restrictions.png)

There are two modes:

- **EXCLUDE**: the deployment will be triggered for all commits EXCEPT the one that have changed ONLY the specified files/folders
- **MATCH**: the deployment will be triggered ONLY if the commit has changed the specified files/folders. If multiple MATCH conditions exist, only one of them has to be true to trigger the deployment.

<Warning>
Important notes:
- The value must be the complete path of the file/folder to be excluded/matched
- The path must NOT start with a forward slash `/`
- Wildcards (`*`) are not supported
- You can use path prefixes for partial matching (e.g., `docs/` will match any file within the docs folder)
</Warning>

To add a restriction without the Console, call `POST /service/{serviceId}/deploymentRestriction`, shared by all these services. `mode`, `type` (only `PATH`) and `value` are required:

```bash
SERVICE_ID="REPLACE_WITH_SERVICE_ID"  # ID of the application, job, Helm, Terraform or container service

qovery api "service/$SERVICE_ID/deploymentRestriction" \
  --field mode=EXCLUDE \
  --field type=PATH \
  --field value=docs/
```

`GET /service/{serviceId}/deploymentRestriction` lists the restrictions of the service. `PUT` and `DELETE /service/{serviceId}/deploymentRestriction/{deploymentRestrictionId}` edit and delete one. The per-kind endpoints (`/application/{applicationId}/deploymentRestriction`, `/job/{jobId}/deploymentRestriction`, `/helm/{helmId}/deploymentRestriction` and `/terraform/{terraformId}/deploymentRestriction`) are deprecated but keep working.

A container's restrictions take effect only while it builds from a Git repository, and the Console does not show them yet: use the API or Terraform.

With Terraform, use the `deployment_restrictions` attribute of `qovery_application`, `qovery_job`, `qovery_helm` or `qovery_container`, with the same `mode`, `type` and `value` fields. `qovery_container` accepts it from provider 1.11.0, on a container built from Git: remove the attribute before switching the container to a registry image.

<Warning>
From provider 1.11.0, leaving `deployment_restrictions` out of a `qovery_application`, `qovery_job`, `qovery_helm` or `qovery_container` deletes the restrictions Qovery holds for the service, those set in the Console included. To keep restrictions managed in the Console, add `lifecycle { ignore_changes = [deployment_restrictions] }` to the resource.
</Warning>

## Container Image Auto-Deploy

A container built from a Git repository deploys on push like an application once its `auto_deploy` is `true`: see [Activation](#activation). The rest of this section is for containers that run an image from a registry.

For container images (not Git repositories), you need to configure your CI/CD pipeline to notify Qovery when a new image tag is available. This can be done through:

- The Qovery API using the `autoDeployContainerEnvironments` endpoint for containers
- The Qovery API using the `autoDeployJobEnvironments` endpoint for lifecycle jobs and cronjobs

See the [API documentation](https://api-doc.qovery.com/) for more details.

For example, after your CI pushes a new tag, deploy it to every environment with auto-deploy turned on that runs a container with the same image name:

```bash
ORGANIZATION_ID="REPLACE_WITH_ORGANIZATION_ID"  # from qovery organization list --json
IMAGE_NAME="REPLACE_WITH_IMAGE_NAME"
NEW_TAG="REPLACE_WITH_NEW_TAG"

qovery api "organization/$ORGANIZATION_ID/container/deploy" \
  --field image_name="$IMAGE_NAME" \
  --field tag="$NEW_TAG"
```

## FAQ

<AccordionGroup>
  <Accordion title="Can I exclude commits from triggering a deployment?">
    Yes, you can use the "Deployment restrictions" feature with EXCLUDE mode to specify files or folders that should not trigger deployments when they are the only changes in a commit.
  </Accordion>

  <Accordion title="Will a stopped service be restarted if auto-deploy is active?">
    No, auto-deploy will not restart a stopped service. The service must be running for auto-deploy to trigger a deployment.
  </Accordion>

  <Accordion title="Is mono-repository supported?">
    Yes, mono-repositories are fully supported. You can have multiple services connected to the same Git repository. Use the "Deployment restrictions" feature with MATCH mode to limit auto-deploy triggers to specific subfolders for each service.
  </Accordion>

  <Accordion title="Does Qovery automatically check the container registry for new image tags?">
    No, Qovery does not automatically monitor container registries. You must notify Qovery when a new image tag is available through:
    - The Qovery Console
    - The Qovery CLI using `qovery container deploy -n "<container-name>" --tag "<tag-name>"` (or `qovery cronjob deploy` and `qovery lifecycle deploy` with `--tag` for jobs)
    - The Qovery API endpoints (`autoDeployContainerEnvironments` or `autoDeployJobEnvironments`)
  </Accordion>
</AccordionGroup>

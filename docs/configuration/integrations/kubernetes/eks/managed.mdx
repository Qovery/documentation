    * **Instance types scopes**: By editing it, you can apply different filters to the node architectures, categories, families, and sizes. On the right, you can view all the instance types that match the applied filters. This means Karpenter will be able to spawn nodes on any of the listed instance types.
      * **Architectures**: by default both `AMD64` and `ARM64` architectures are selected.

### Resources

Qovery deploys two node pools by default:

- **Stable node pool**: Used for single instances and internal Qovery applications. For example, any containerized databases or application having the number of minimum instances set to 1, will be deployed on this nodepool. On this nodepool the consolidation is deactivated by default.
- **Default node pool**: Designed to handle general workloads and serves as the foundation for deploying most applications.

Additional optional node pools can be enabled:

- **GPU node pool**: Can be enabled if you want to run GPU workloads on your cluster. You can select the GPU instance types you want to use on this nodepool.
- **Cronjob node pool**: A dedicated node pool for Qovery cron jobs. When enabled, a Karpenter NodePool named `cronjob` is created with a `nodepool/cronjob: NoSchedule` taint. Qovery cron jobs automatically receive the appropriate toleration and a required node affinity toward this nodepool, so they always run there. This helps isolate cronjob workloads from long-running services on shared nodes. The cronjob nodepool supports consolidation scheduling, resource limits (same as the stable nodepool) and its own spot instances toggle. The node affinity is required (hard): whenever you enable or disable this nodepool, **you must redeploy every cron job** so they pick up the updated scheduling configuration. There is no automatic fallback to the default node pool. Cron jobs deployed before the nodepool was enabled will not run on it until they are redeployed, and cron jobs deployed while the nodepool was enabled will stay in `Pending` if the nodepool is later disabled and they are not redeployed.

#### Settings for nodepools:

- **Instance types**: Define the list of instance types that can be used. (Shared for Stable and Default nodepools)
- **Spot instances**: Enable or disable spot instances, per node pool. Enabling it on the stable node pool is discouraged: it hosts single-instance workloads that don't tolerate interruptions.
- **Node disk size (GB)**: Specify the disk capacity allocated per worker node, determining the amount of data each node can store. (Shared for Stable and Default nodepools)
- **Consolidation schedule** _(Stable and Cronjob nodepools only)_: Optimizes resource usage by consolidating workloads onto fewer nodes. This feature is not available for the default nodepool, as consolidation can happen at any time. We recommend enabling this option; otherwise, nodes will never be consolidated, leading to unnecessary infrastructure costs.
- **Block node drift** _(Stable nodepool only)_: Define one daily UTC window during which Karpenter does not replace drifted stable nodes. A node drifts when its configuration no longer matches the node pool spec, for example after an instance type change, a Kubernetes upgrade or an AMI security update. By default Karpenter replaces drifted nodes as soon as it detects them, which restarts the single-instance workloads and containerized databases running on the stable node pool. With this option enabled, replacements wait until the window ends. Set a start time (UTC) and a duration using `H` for hours and `M` for minutes (e.g. `2H10M` in the Console, `PT2H10M` in ISO-8601 format through the API); the maximum is 23 hours, so at least one hour per day remains available for drift. The window repeats every day. New nodes created during the window already use the updated configuration, only the replacement of existing nodes is deferred.
- **Node pool limits**: Configure CPU and memory limits to ensure nodes stay within defined resource constraints, preventing excessive costs.

## Defining cluster node constraints to run your Services

### Define if your service can run on an on-demand instance

When using spot instances in your cluster, you may want to ensure that certain critical services, such as databases or essential applications, are always deployed on on-demand instances.

To specify that a service should be deployed on an `on-demand` instance, manually set the `deployment.affinity.node.required` advanced setting to:

```json
{ "karpenter.sh/capacity-type": "on-demand" }
```

### Define the instance type to run your service

In some cases, you may need to ensure that a specific service runs on a particular instance type to meet performance, compliance, or cost requirements.

For example, to assign a service to the t3a.xlarge instance type, manually set the `deployment.affinity.node.required` advanced setting to:

```json
{ "node.kubernetes.io/instance-type": "t3a.xlarge" }
```

<Info>
  The specified instance type must be included in the list of instance types
  defined in the [NodePool configuration](#resources).
</Info>

### Change the node pool of your service when using Helm

When using Helm, you can update the `affinity` field in your `values.yaml` file to target a specific node pool for your service. For example you can switch from the `default` to the `stable` nodepool:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: karpenter.sh/nodepool
              operator: In
              values:
                - stable
```

And you also have to add tolerations:

```yaml
tolerations:
  - effect: NoSchedule
    key: nodepool/stable
    operator: Exists
```

## Restricted Credentials

<Info>
Restricted Credentials is not enabled by default: Qovery Support enables it per organization. Until then, the **Use restrictive permissions** option is not displayed in the Console. To use it, contact [Qovery Support](/getting-started/useful-resources/help-and-support) through your usual channel (in-app chat, Slack, or email) to request access.
</Info>

By default, a cluster uses a single set of credentials for every operation, so the IAM role behind it keeps the unrestricted IAM and KMS permissions (`iam:*`, `kms:*`) listed in [Connect Your AWS Account](#connect-your-aws-account) at all times. Restricted Credentials replace it with two IAM roles in your AWS account, each created by its own CloudFormation template (see [Create the IAM roles](#create-the-iam-roles)). The role allowed to change the IAM roles, policies and KMS keys of the cluster is then only used when it is actually needed.

Each of the two credentials uses the [STS Assume Role](#connect-your-aws-account) method and targets its own IAM role:

**Extended credentials**: used only for operations that need the extended permissions:

- Creating the cluster
- Deleting the cluster
- Any change to the IAM roles and policies of the cluster, for example when enabling [Secret Manager Access with AWS Automatic Authentication](/configuration/integrations/secret-managers/aws-secrets-manager), metrics, or [KEDA](/configuration/application#event-driven-autoscaling-with-keda)
- Any other operation for which Qovery explicitly requests them

**Restricted credentials**: used for day-to-day operations:

- Regular weekly cluster updates
- Service deployments, including the blueprints

<Warning>
Once Restricted Credentials is enabled, [Terraform services](/configuration/terraform) that use the cluster credentials (the default behavior) are always deployed with the restricted credentials.

Review your Terraform services before requesting the feature: only Terraform services managing resources that rely on `iam:*` or `kms:*` are concerned. Once your cluster uses Restricted Credentials, [update these Terraform services](#update-your-terraform-services) before their next deployment.
</Warning>

### Create the IAM roles

Each role is created by its own CloudFormation template. Create both stacks in the AWS account of your cluster:

| Role | Default name | CloudFormation |

| Restricted | `qovery-restricted-user-role` | [Launch stack](https://console.aws.amazon.com/cloudformation/home?#/stacks/quickcreate?templateURL=https%3A%2F%2Fqovery-restricted-user-role.s3.amazonaws.com%2Ftemplate.json&stackName=qovery-restricted-user-role) · [View template](https://qovery-restricted-user-role.s3.amazonaws.com/template.json) |

The IAM and KMS permissions of both roles are scoped to the resources Qovery creates for the cluster: IAM identities named after Qovery conventions (`qovery-*`, `Karpenter*`, ...) and KMS keys tagged `QoveryProduct=EKS`. The `Metadata` of the role resource in each template explains why each permission is needed.

### Disable the extended credentials IAM role

As soon as Qovery no longer needs the extended credentials (for example, once the cluster is installed), you can disable them directly from your AWS account. To do so, replace the trust relationship of the extended IAM role with a policy that denies `sts:AssumeRole`:

<Steps>
  <Step title="Open the extended IAM role">
    In the AWS Console, go to **IAM** > **Roles** and select the IAM role targeted by the extended credentials.
  </Step>

  <Step title="Edit the trust policy">
    Open the **Trust relationships** tab, click **Edit trust policy** and replace its content with:

    ```json
    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Deny",
          "Principal": { "AWS": "*" },
          "Action": "sts:AssumeRole"
        }
      ]
    }
    ```

    Click **Update policy** to save.
  </Step>
</Steps>

Qovery can no longer assume the extended IAM role. The role and its permissions policy are kept in your AWS account, so you can re-enable the extended credentials at any time. The restricted credentials keep being used for weekly cluster updates and service deployments.

<Info>
Changing the trust policy only blocks new role assumptions. Temporary credentials that Qovery obtained before the change remain valid until they expire. To cut access immediately, open the **Revoke sessions** tab of the extended IAM role and click **Revoke active sessions** (see the [AWS documentation](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_use_revoke-sessions.html)). This interrupts any operation Qovery is running with the extended credentials.
</Info>

<Warning>
While the extended credentials are disabled, Qovery cannot perform operations that require them, such as deleting the cluster or enabling a feature that needs additional AWS permissions.
</Warning>

### Update your Terraform services

Once your cluster uses Restricted Credentials, make the Terraform services that manage resources relying on `iam:*` or `kms:*` assume a dedicated IAM role that has the permissions they need.

<Info>
Apply these steps only once your cluster uses Restricted Credentials: the dedicated IAM role only trusts the restricted IAM role, so a Terraform service running with other credentials cannot assume it.
</Info>

<Steps>
  <Step title="Create a dedicated IAM role">
    In your AWS account, create an IAM role with the IAM and KMS permissions your Terraform code needs. Set its trust relationship so that the [restricted IAM role](#create-the-iam-roles) can assume it. Replace `<restricted-role-arn>` with the **RoleARN** output of the restricted role stack:

    ```json
    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Allow",
          "Principal": { "AWS": "<restricted-role-arn>" },
          "Action": "sts:AssumeRole"
        }
      ]
    }
    ```
  </Step>

  <Step title="Assume the role in your Terraform code">
    Add an `assume_role` block to the `provider "aws"` block of your Terraform code:

    ```hcl
    variable "aws_role_arn" {
      type = string
    }

    provider "aws" {
      # ...your existing provider configuration

      assume_role {
        role_arn = var.aws_role_arn
      }
    }
    ```
  </Step>

  <Step title="Set the role ARN">
    Qovery detects the `aws_role_arn` variable declared in `main.tf` or `variables.tf` and exposes it as `tf_var_aws_role_arn` (see [Terraform variables](/configuration/terraform)). Set it to the ARN of the dedicated IAM role, then redeploy the Terraform service.
  </Step>
</Steps>

The Terraform service still starts with the restricted credentials, then uses the dedicated IAM role to manage your IAM and KMS resources.

This page takes an application from a Git repository to a running service, using only the terminal. Every step is a command you can copy, so a script or a coding agent can follow it from start to end. The [agent skills](/getting-started/quickstart/ai-agent) do the same work for you; this page shows what they run.

Qovery has no repository manifest: there is no `qovery.yml` to write. Everything below is created in Qovery through the API, and `qovery api` handles authentication for you.

## Before you start

<Check>A Qovery account. The first `qovery auth` creates one, and the [Free plan](https://www.qovery.com/pricing) needs no credit card.</Check>
<Check>A cluster in your organization: your own Kubernetes cluster ([install it](/getting-started/installation/kubernetes)), a cluster managed by Qovery, or a local one from `qovery demo up` ([local demo](/getting-started/quickstart/docker)).</Check>
<Check>A repository on GitHub, GitLab or Bitbucket with a `Dockerfile`, and the port your app listens on.</Check>

Some steps need a person, once per organization:

| Step | Why | Done by |
| --- | --- | --- |
| Sign in with `qovery auth --headless` | Opens a browser link to approve | The person who owns the account |
| Create the cluster | Needs cloud credentials or a local Docker | Platform owner, or `qovery demo up` |
| Create the token on your Git provider | Only you can create a token on your GitHub, GitLab or Bitbucket account | Repository owner |

Everything else on this page can run unattended.

## 1. Install the CLI and sign in

```bash
curl -s https://get.qovery.com | bash
qovery auth --headless
qovery auth status
```

`qovery auth --headless` prints a link to open in a browser. `qovery auth status` shows whether you are signed in, without printing the token. Other install methods (Homebrew, Windows, pinned releases) are on the [CLI page](/cli/overview).

<Note>
`qovery context set` is interactive. In scripts and agents, pass IDs in the API paths and names with `--organization`, `--project` and `--environment` instead.
</Note>

## 2. Find your organization and cluster

```bash
qovery api organization
qovery api organization/<organizationId>/cluster
```

Each call returns JSON with a `results` array. Keep the `id` of your organization and of the cluster you want to deploy on.

## 3. Give Qovery read access to the repository

Skip this step if your organization already has Git access set up (a Git token or the Git provider connected in the Console).

Create a token on your Git provider with read access to the repository (see [Git repository access](/configuration/organization/git-repository-access) for the permissions per provider), put it in an environment variable, then register it in Qovery:

```bash
cat <<EOF | qovery api organization/<organizationId>/gitToken --method POST --input -
{
  "name": "deploy-token",
  "type": "GITHUB",
  "token": "$GIT_PROVIDER_TOKEN"
}
EOF
```

`type` is `GITHUB`, `GITLAB` or `BITBUCKET`. Bitbucket also needs a `workspace` field. Keep the `id` from the response: it is the `git_token_id` used in step 5.

## 4. Create a project and an environment

```bash
qovery api organization/<organizationId>/project --method POST --field name=storefront

qovery api project/<projectId>/environment --method POST \
  --field name=production \
  --field mode=PRODUCTION \
  --field cluster=<clusterId>
```

`mode` is `DEVELOPMENT`, `STAGING` or `PRODUCTION`. Keep both `id` values.

## 5. Create the application

Save this as `application.json` and change the values to match your repository:

```json
{
  "name": "api",
  "git_repository": {
    "url": "https://github.com/acme/storefront.git",
    "branch": "main",
    "root_path": "/",
    "provider": "GITHUB",
    "git_token_id": "<gitTokenId>"
  },
  "build_mode": "DOCKER",
  "dockerfile_path": "Dockerfile",
  "cpu": 500,
  "memory": 512,
  "min_running_instances": 1,
  "max_running_instances": 1,
  "ports": [
    {
      "name": "http",
      "internal_port": 8080,
      "external_port": 443,
      "protocol": "HTTP",
      "publicly_accessible": true
    }
  ],
  "healthchecks": {
    "liveness_probe": {
      "type": { "tcp": { "port": 8080 } },
      "initial_delay_seconds": 30,
      "period_seconds": 10,
      "timeout_seconds": 5,
      "success_threshold": 1,
      "failure_threshold": 3
    }
  },
  "auto_deploy": true
}
```

```bash
qovery api environment/<environmentId>/application --method POST --input - < application.json
```

- `git_repository.url` must end in `.git`.
- `root_path` is the folder that holds the `Dockerfile`, for example `/backend` in a monorepo.
- `internal_port` is the port your app listens on. Use an `http` probe instead of `tcp` if the app has a health endpoint.
- Remove `git_token_id` if your organization uses the Git provider connected in the Console.
- `cpu` is in millicores and `memory` in MiB.

The full schema, with every optional field, is in the [API reference](/api-reference/introduction). `qovery api spec` prints the same OpenAPI file in the terminal.

## 6. Deploy

```bash
qovery application deploy \
  --organization "<organization name>" \
  --project storefront \
  --environment production \
  --application api \
  --commit-id latest \
  --watch
```

`--commit-id latest` deploys the newest commit of the branch. `--watch` follows the deployment until it succeeds or fails.

To deploy several services of the environment at once, use `qovery environment deploy` with `--applications`, `--containers` or `--services`. See the [environment commands](/cli/commands/environment).

## 7. Check it worked

```bash
qovery application list --organization "<organization name>" --project storefront --environment production --json
qovery api application/<applicationId>/link
```

The list shows the application and its status. The `link` call returns the public URL of each exposed port. Open it to reach your app.

If the deployment failed, read the logs:

```bash
qovery log --organization "<organization name>" --project storefront --environment production --application api
```

Build and runtime errors and their fixes are in [Troubleshooting](/getting-started/troubleshoot/overview).

## Commands and files that do not exist

Agents often guess these. None of them exist:

| Do not use | Use instead |
| --- | --- |
| `qovery init`, `qovery.yml`, `.qovery.yml`, `.qovery.toml` | Nothing to create in the repository. Configuration lives in Qovery: API, CLI, Console or [Terraform](/terraform-provider/overview) |
| `qovery deploy` | `qovery application deploy` or `qovery environment deploy` |
| `qovery application create`, `qovery database create`, `qovery project create`, `qovery environment create` | `qovery api <path> --method POST`, as on this page. Only container services have a create command: `qovery container create` |
| `qovery token create` | `qovery token` (interactive), the Console, or the `/qovery-policy-token` skill for a [scoped token](/configuration/organization/api-policy-token) |
| `qovery context set --organization ...` | `context set` takes no flags. Pass `--organization`, `--project`, `--environment` to each command |
| An IAM user with `AdministratorAccess` for Qovery | The IAM role created by the CloudFormation stack in [Install on AWS](/getting-started/installation/aws) |

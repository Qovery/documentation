The Qovery Operator connects a Kubernetes cluster you already run to Qovery. You create the cluster in the Qovery Console, install the Operator once with Helm, and Qovery then installs and updates the Qovery stack on the cluster from a platform profile.

<Info>
This page describes the Operator-based installation, available for AWS, GCP and Scaleway clusters. For other providers, or to install Qovery with the Qovery CLI, see [BYOK (Bring Your Own Kubernetes)](/configuration/integrations/kubernetes/byok).
</Info>

<Warning>
This installation is in **Preview**. Its capabilities are still incomplete and may change: see [Current limitations](#current-limitations) before connecting a production cluster.
</Warning>

## How it works

- Qovery never stores the kubeconfig of your cluster. You install the Operator yourself, with your own `kubectl` and `helm` access.
- The Operator runs in the `qovery` namespace. It opens an outbound connection to Qovery and runs the Qovery deployments as Kubernetes Jobs inside your cluster.
- The platform profile of the cluster lists the components Qovery installs and their settings. Qovery installs them in this order:
  - **Qovery stack**: the Qovery agent and shell agent.
  - **Log infra**: Loki and Alloy, for application logs.
  - **Gateway API**: Envoy Gateway, which exposes your applications.
  - **DNS and certificates**: cert-manager and ExternalDNS, for the Qovery-provided domain and its TLS certificates.
- Application images are built inside your cluster and pushed to a registry Qovery creates from your cloud credential: Amazon ECR on AWS, Artifact Registry on GCP, Scaleway Container Registry on Scaleway.

## Prerequisites

<Check>A running Kubernetes cluster on AWS (EKS), GCP (GKE) or Scaleway (Kapsule)</Check>
<Check>`kubectl` access to the cluster and `helm` installed on your machine</Check>
<Check>A cluster that does not already run cert-manager, ExternalDNS or Envoy Gateway</Check>
<Check>A default StorageClass (`kubectl get storageclass`), unless Loki stores logs in object storage. Recent EKS versions do not create one.</Check>
<Check>A working cluster DNS (CoreDNS) that resolves public names</Check>
<Check>Outbound internet access from the cluster to Qovery and to public container registries</Check>
<Check>A Qovery cloud credential for the provider of the cluster. You can create it during the installation.</Check>

### Credential permissions

The cloud credential lets Qovery create the cluster registry, push the images it builds and clean them up. It does not need access to the Kubernetes cluster itself.

<Tabs>
  <Tab title="AWS">
    The credential only needs Amazon ECR. Use access keys limited to this policy, or a role with the same policy:

    ```json
    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Sid": "EcrLogin",
          "Effect": "Allow",
          "Action": "ecr:GetAuthorizationToken",
          "Resource": "*"
        },
        {
          "Sid": "CredentialCheck",
          "Effect": "Allow",
          "Action": "ecr:DescribeRepositories",
          "Resource": "arn:aws:ecr:us-east-1:<ACCOUNT_ID>:repository/*"
        },
        {
          "Sid": "ClusterRegistry",
          "Effect": "Allow",
          "Action": [
            "ecr:DescribeRepositories",
            "ecr:CreateRepository",
            "ecr:PutLifecyclePolicy",
            "ecr:TagResource",
            "ecr:ListTagsForResource",
            "ecr:DescribeImages",
            "ecr:BatchDeleteImage",
            "ecr:DeleteRepository",
            "ecr:BatchCheckLayerAvailability",
            "ecr:InitiateLayerUpload",
            "ecr:UploadLayerPart",
            "ecr:CompleteLayerUpload",
            "ecr:PutImage",
            "ecr:BatchGetImage",
            "ecr:GetDownloadUrlForLayer"
          ],
          "Resource": "arn:aws:ecr:<CLUSTER_REGION>:<ACCOUNT_ID>:repository/*"
        }
      ]
    }
    ```

    - Keep the `us-east-1` statement even if the cluster runs in another region: Qovery checks the credential there.
    - The EKS node role must be able to pull from ECR in the same account, for example with the `AmazonEC2ContainerRegistryPullOnly` managed policy.
    - Managed databases and Terraform services that use the cluster credentials need their own permissions.
  </Tab>

  <Tab title="GCP">
    Qovery creates, reads and deletes Artifact Registry repositories and images in the project of the credential, in the cluster region.

    - Grant the service account the **Artifact Registry Administrator** role (`roles/artifactregistry.admin`) on the project.
    - With a JSON key, Qovery checks the key by listing the Cloud Storage buckets of the project: the service account also needs the `storage.buckets.list` permission. A Workload Identity Federation credential is checked without it.
  </Tab>

  <Tab title="Scaleway">
    Qovery creates, reads and deletes Container Registry namespaces and images in the project of the API key, in the cluster region.

    - Give the API key the **ContainerRegistryFullAccess** permission set on the project.
    - Qovery checks the key by listing the Container Registry namespaces of the `fr-par` region, whatever the cluster region.
  </Tab>
</Tabs>

## Create the cluster

<Steps>
  <Step title="Open the cluster creation page">
    In the Qovery Console, go to **Clusters** and create a new cluster. Under **Connect existing cluster (BYOK)**, select **AWS**, **GCP** or **Scaleway**.

    <Frame>
      <img src="/images/byok-operator/add-cluster.png" alt="Add cluster page with the Connect existing cluster (BYOK) section" />
    </Frame>
  </Step>

  <Step title="Fill in the general information">
    - **Cluster name**: the name of the cluster in Qovery.
    - **Production cluster**: off by default. Turn it on for a production cluster.
    - **Credentials**: select a cloud credential of the provider, or create one.
    - **Region**: the region of your cluster. On Scaleway, select the zone of the cluster, for example `fr-par-1`.

    Click **Continue**.

    <Frame>
      <img src="/images/byok-operator/general-information.png" alt="Connect AWS cluster step" />
    </Frame>
  </Step>

  <Step title="Configure the Qovery Operator">
    Leave the settings as they are, unless you want the Operator and its Jobs pinned to a specific node group. Click **Continue**: Qovery creates the cluster and its registry.

    <Frame>
      <img src="/images/byok-operator/configure-operator.png" alt="Configure Qovery Operator step" />
    </Frame>
  </Step>

  <Step title="Install the Qovery Operator">
    1. Download the Helm values file `values.yaml`. It contains the credential of the cluster: keep it private and delete it once the Operator is installed.
    2. From the folder of the values file, with a kubeconfig pointing to your cluster, run the Helm command shown in the Console.

    Keep the page open. Once the Operator connects to Qovery, the Console opens the profile of the cluster. The Operator status is then shown at the bottom of the profile sidebar.

    <Frame>
      <img src="/images/byok-operator/install-operator.png" alt="Install Qovery Operator step with the Helm values file and command" />
    </Frame>
  </Step>

  <Step title="Configure and deploy the platform profile">
    On the profile page, review the settings of each component, then click **Save and deploy**. Qovery installs the components of the profile through the Operator. Follow the progress in the cluster logs.

    <Frame>
      <img src="/images/byok-operator/cluster-profile.png" alt="Profile page of a cluster connected with the Qovery Operator" />
    </Frame>
  </Step>
</Steps>

Once the deployment succeeds, you can deploy your applications on the cluster.

## Current limitations

- **DNS**: applications are exposed on the domain provided by Qovery. The DNS provider of the cluster cannot be changed.
- **Cluster settings**: the platform profile replaces most cluster advanced settings. Only the settings that still apply to these clusters are shown.
- **Metrics**: Qovery installs no metrics stack on these clusters.
- **Existing installations**: Qovery does not adopt an existing cert-manager, ExternalDNS or Envoy Gateway installation. Use a cluster without them.
- **Removal**: deleting the cluster in Qovery does not uninstall the Operator or the platform components. Remove them yourself with `helm uninstall` in the `qovery` namespace.

## Troubleshooting

<AccordionGroup>
  <Accordion title="The Operator does not connect">
    - Check that the Operator pod is running: `kubectl -n qovery get pods`.
    - Read its logs: `kubectl -n qovery logs deployment/qovery-operator --tail=100`.
    - A `gateway communication error` or `transport error` at startup is often a cluster DNS issue. Check that a Pod resolves the Qovery endpoint:

      ```bash
      kubectl -n default run qovery-dns-preflight --rm -i --restart=Never --image=busybox:1.36 -- nslookup engine.qovery.com
      ```

      The lookup must return an address. A timeout or `no servers could be reached` means the cluster DNS must be fixed first.
    - Check that the cluster can reach the internet.
  </Accordion>

  <Accordion title="Loki stays Pending">
    The Loki volume cannot be created without a default StorageClass. Check `kubectl get storageclass`, mark one as default, then deploy the cluster again.
  </Accordion>

  <Accordion title="The credential is refused when the cluster is created">
    Qovery checks that the credential can use the registry of the provider in the cluster region before it creates anything. Compare the credential with [Credential permissions](#credential-permissions).
  </Accordion>
</AccordionGroup>
